# Ironlog — Full-Stack Calorie & Macro Tracker

A training-aware nutrition tracker built for lifters. Unlike generic calorie
apps, Ironlog treats **training days and rest days as first-class modes** and
cycles your calorie/carb targets between them while holding protein steady — the
way most bodybuilding nutrition is actually run.

**Stack:** FastAPI + SQLAlchemy 2.0 (Python) · React 18 + TypeScript + Vite ·
TanStack Query · Recharts.

---

## Features

- **Today** — a calorie gauge plus protein/carb/fat rails showing eaten vs.
  target vs. remaining for the selected day. Protein gets top billing.
- **Log** — search a reusable food library, add by servings, or quick-add a
  one-off food with custom macros. Entries are grouped by meal.
- **Trends** — bodyweight over time with a 7-day moving average (to cut through
  daily water-weight noise), and a calories-vs-target bar chart.
- **Goals** — enter your stats and get target suggestions from the
  Mifflin–St Jeor equation, then fine-tune separate training-day and rest-day
  targets and save them.
- **Day-type toggle** — flip any day between *training* and *rest*; the Today
  view re-compares your intake against that day's target set.

## Running it

### 1. Backend (terminal 1)

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python seed.py                      # creates calorie_tracker.db with demo data
uvicorn app.main:app --reload       # http://localhost:8000  (docs at /docs)
```

### 2. Frontend (terminal 2)

```bash
cd frontend
npm install
npm run dev                         # http://localhost:5173
```

The Vite dev server proxies `/api/*` to the backend on port 8000, so just open
the frontend URL and everything is wired up. Skip `seed.py` if you'd rather
start from an empty database.

## Two design decisions worth calling out

**Sync SQLAlchemy, intentionally.** The route handlers are plain `def`
functions, not `async def`. FastAPI runs sync handlers in a worker threadpool,
which keeps the blocking SQLite driver off the event loop — so one slow query
never stalls the whole server. Going `async def` here would put blocking DB
calls directly on the loop unless paired with an async driver, which buys
nothing for a SQLite-backed personal app and adds real footguns. (Swap in
`asyncpg` + `async def` if this ever grows into a high-concurrency Postgres
service.)

**Log entries snapshot their macros.** A `LogEntry` stores the calories and
macros *as they were at log time* rather than only pointing at a `Food` row.
This means editing a food's macros — or deleting the food entirely — never
silently rewrites your history. The `food_id` foreign key is kept as a soft
link (it nulls out if the food is removed) purely for convenience, not as the
source of truth for what you ate.

## Notes

- `calorie_tracker.db` is generated by `seed.py` and is not included; it's
  created on first run.
- Nutrition targets use Mifflin–St Jeor for BMR, scaled by an activity factor
  for TDEE, then adjusted by goal (cut / maintain / bulk) per day type. These
  are reasonable starting points, not medical advice — adjust to your own
  trends.
